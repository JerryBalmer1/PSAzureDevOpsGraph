# v0.2.0 — History unification

**Scores carried from v0.1.0, not re-earned this plan.**

## What this plan did

One merge commit on `main`, joining two histories that had never met:

- `2c745310` "Initial commit" — the repository as GitHub created it, holding a
  one-line `README.md` and nothing else.
- `79e02fba` — run 002's build, tagged `v0.1.0`, rooted at `ea4c4fd4` "Seed".

The merge used `--allow-unrelated-histories`. Both roots are preserved. Nothing
was forced and no history was rewritten.

One collision, `README.md`, present on both sides as an add/add. Resolved by
taking the module's README wholesale — the `main` side held only the title line.

This file, and the annotated tag `v0.2.0`, are the only other additions. No
source file, test, or build file changed in this plan.

## The finding it resolves

Pass 0018 was asked to fast-forward `main` to `v0.1.0` and could not. The two
lines had **no common ancestor** — `git merge-base` exited 1 with no output, and
git's own `--dry-run` rejected the push as non-fast-forward.

The cause is structural rather than accidental. `Reset-Target.ps1` materialises
the seed into a fresh repository with its own `git init`, so every run branch it
produces is an orphan root. Run 002 was pushed to this remote as exactly that.
No tag on such a branch can ever fast-forward a `main` that descends from
GitHub's initial commit.

Pass 0018 stopped rather than forcing the push, which is what the governing
decision required, and reported four options. The operator chose the merge.

## What changes from here

`main` now descends from both roots, so it is an ancestor of any future work
branched from it. From this point the rule that `main` follows tags by
fast-forward is satisfiable, and it is satisfied the ordinary way — no further
unrelated-history merges should ever be needed on this repository.

The distinction that made this necessary is now deliberate:

- **The deliverable line** is `main` and the tags on it. Future plans branch
  from `main`, commit their work there, and tag it.
- **The measurement line** is whatever `Reset-Target.ps1` produces into scratch
  for wiped-state reliability runs. Its orphan-root property is load-bearing —
  it marks a measurement branch as structurally distinct from the deliverable
  line. Measurement branches are never merged to `main` and never tagged.

`Reset-Target.ps1` is unchanged.
