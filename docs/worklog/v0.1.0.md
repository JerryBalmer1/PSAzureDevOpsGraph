# Worklog — v0.1.0

Why the module is shaped the way it is. What changed is in the changelog; this
is the reasoning that would otherwise have to be rediscovered.

## Parsing and resolution are two commands

The brief asks for it and the cost of merging them is concrete: a combined
command reports resolution failures as parsing results, and there is then no way
to tell which half was wrong. Parsing is testable against a file on disk with no
credentials, which is why most of this repository's tests need no PAT.

## Which optional fields get written, and why

The schema makes almost every field optional, so each one is a decision about
whether there is a positive fact to state. An absent optional field means *not
stated*, which is a quieter claim than writing a redundant value - and a
convention chosen wrongly costs one difference per record, not one difference.

The first scoring run against the oracle produced 26 differences from **four**
decisions, which is the whole point of grouping differences by mechanism before
reading the number:

| Written | Not written | Why |
|---|---|---|
| `repo` on `pipeline` and `yaml` nodes | `repo` on `repo` nodes | Where a pipeline lives cannot be read off its id; a repo node's `name` already is the repository. |
| `path` on `yaml` nodes | `path` anywhere else | Only a file has one. |
| `ref` on every edge but `definition` | `ref` on `definition` | A definition edge is a claim about the Azure DevOps project, not about a file. |
| `refKind` on `unresolved` edges | `refKind` elsewhere | Everywhere else `kind` already **is** the reference kind. |
| `alias` on `repositoryResource` and `pipelineResource` | `alias` on `template`, `extends`, `checkout` | A resources entry declares a local handle that *differs* from the thing it names. On a template the alias is a suffix of `ref`; on a checkout the `ref` **is** the alias. |

Each of the last two rows was got wrong first time in opposite directions -
`refKind` omitted correctly, `alias` written everywhere for the sake of a
consistency the contract does not want - and the second cost 8 differences.

## A reason is a code and an explanation

`reason` on an unresolved edge is not a bare code. It is
`<code>: <what was tried and what was found>`:

```
file-not-found: resolved to pipelines/templates/missing-steps.yml in pipelines-main, which does not exist
alias-not-declared: 'ghostTemplates' is not in resources.repositories of pipelines/p09.yml, so the repository is unknown and the path cannot be resolved at all
```

The code says which fix is needed; the explanation says *where to make it*, and
names the resolved path rather than the reference text - which is the half a
reader cannot reconstruct, because it is the output of whichever of the two
resolution rules ran.

## The repositories endpoint is a lookup table

It is called once, to turn a repository name into something the items route can
use and to know which names exist. It does **not** produce nodes: a graph with a
node per repository in the project answers "what is in this project" instead of
"what do these pipelines depend on".

But "only what a reference names" is too narrow, and that is the one difference
the first scoring produced that was not a convention. A repository is a node
when the graph has something **in** it - a pipeline definition or a YAML file -
*or* when a reference names it. `consumer-app` holds two pipelines and three
YAML files and nothing in the fixture references it; it is still where those
pipelines live, and the oracle has a node for it with no edges at all. The empty
`ClaudeTesting` repository holds nothing and is referenced by nothing, and is
correctly absent - which is the case the "not from the endpoint" rule exists to
protect.

Twenty-five of the twenty-six first-shot differences were three conventions.
The twenty-sixth was this, and it was the only one that was a defect in the
traversal rather than in a field.

## powershell-yaml is in the manifest, not in Requirements.psd1

It is a runtime dependency: a machine that imports this module needs it whether
or not it ever runs a build. `Requirements.psd1` holds build tools only. Writing
a dependency in both files creates two facts that must agree and are edited in
different places.

## Coverage target

70%, declared once to Pester and read back off the result by the gate, so there
is one number rather than two that must agree. The REST error branches are
covered by mocking `Invoke-WebRequest` rather than by lowering the target.
